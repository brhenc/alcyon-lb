Mechanism (`include/haproxy/dynbuf.h`, `src/dynbuf.c`), consistent with the counts above:
`tune.buffers.reserve` (default `RESERVED_BUFS` 4) buffers per thread are taken at thread start
into `th_ctx->emergency_bufs` and the pool limit is raised by one per reserved buffer
(`dynbuf.c:283-286`). `b_alloc(buf, crit)` maps the criticality to one of four per-thread queues
(`DB_CRIT_TO_QUEUE`: `DB_MUX_TX` → 0, `DB_CHANNEL` → 1, `DB_SE_RX` → 2, `DB_MUX_RX` → 3; 0 is the
most critical), and refuses (the caller queues a `buffer_wait`) when **any queue at its level or a
more critical one is non-empty**, or when `emergency_bufs_left * 3 < q * reserve` (queue 3, a
connection's first receive buffer, may only allocate while the reserve is **full**; queue 0 may
drain it). A failed `pool_alloc` falls back to an emergency buffer. `b_free` refills the reserve
before giving to the pool. `offer_buffers(from, count)` (called where buffers are released) wakes
up to `count` waiters, most critical queue first, **on the current thread only**. `show pools`
counts none of this as a failure (`0 failures` in every HAProxy run); `show activity` has
`pool_fail` and `buf_wait` per thread (e.g. `pool_fail: 2074 [ 887 1187 ] ; buf_wait: 1124 [ 508 616 ]`).

### 1.3 Answers

- **Who is served, in what order.** HAProxy serves the streams already under way first: a new
  connection's first buffer (queue 3) waits until no other queue has waiters and the thread's
  reserve is full again, so fast GETs are served only after slow readers finish (in every drain
  run, whatever the reserve). Inside queue 3 the list is FIFO (`LIST_APPEND`, offered from the
  head), but the order observed is not (5, 4, 2, 1, 0, 3): all woken waiters are retried in one
  pass and requeue. Per thread: a waiter on one thread is not served by a buffer freed on the
  other; a fast GET on a thread whose reserve is full is served at once while another thread's
  waiters wait.
- **Latency of a fast GET while buffers are exhausted.** Until the in-flight work on its thread
  finishes and the reserve refills: 4-28 s here, or the client timeout. Never an error before it.
- **What a waiter logs.** Waiting for its first buffer, nothing until served; then an ordinary
  line (timers 0: `Tq`/`Tw`/`Tc` do not show the wait; the date is when it was served). Waiting on
  the response side: the wait is in `Tr`. **Timeout while waiting: `timeout client`, `408`, `cR--`,
  `-1/-1/-1/-1/<timeout>`, `fe/<NOSRV>`, `"<BADREQ>"`**, the 408 delivered (it may itself wait
  for a buffer: one was sent 2 s after its timer, when the readers' timeouts freed buffers).
- **`show pools` / `show info` while waiting.** HAProxy: `16 allocated, 16 used`, `0 failures`;
  `show info` has no buffer field; `show activity` `pool_fail`/`buf_wait` count; under full
  exhaustion the CLI itself waits (empty answers). Ibex: `8 allocated`, `N failures` counting
  each refused take; the CLI answers.
- **What `tune.buffers.reserve` changes.** Raises the cap by `nbthread × reserve` and preallocates
  those; gates queue 1-3 allocations on how full the reserve is. It does not let new connections
  overtake in-flight streams.
- **Ibex today is worse than HAProxy on every shape**: it cuts established responses (`ID--`)
  where HAProxy never failed a stream, and resets new connections instead of making them wait.

## 2. Design decided from it

1. **Per-thread queues by class**, four as HAProxy: `MuxTx` 0 (a buffer to send to the client,
   local responses), `Channel` 1 (`htx_buf`), `SeRx` 2 (a receive buffer for the server side),
   `MuxRx` 3 (a connection's receive buffer from the client). Ibex's sites: `proxy.rs` `req`
   read (`MuxRx`), `rep` read from the server (`SeRx`), `rep` for a local response (`MuxTx`),
   `xprt.rs` TLS rx (`MuxRx` client side, `SeRx` server side). A take refused with waiters at its
   class or above queues; one taking from a thread-local cache never sees the queue.
2. **No stream fails for want of a buffer while its timeouts run**: every site that calls
   `fail_alloc` today parks the session instead (no I/O interest on that side, timers kept). The
   timeouts decide, with HAProxy's flags: `timeout client` before the request → `408 cR--`
   `-1/-1/-1/-1/<timeout>` `<BADREQ>` (measured); on the response side the client's timeout
   gave `cD--` (measured); `timeout server` while waiting on the response side was **not
   measured** and is checked on the oracle before that site is built.
3. **The queue allocates nothing**: an intrusive list through the session slab (two `u32` links
   and a class byte per session; the waiter is the session itself, so a session freed while
   waiting unlinks in O(1) and nothing leaks), and a 4-bit `bufq_map` per thread.
4. **Wake on give**: a standard buffer given back on a thread with `bufq_map != 0` marks the
   first waiter of the most critical queue runnable (one per buffer, HAProxy's `count`), same
   thread only. The check is on the give path; the take path gains nothing when a buffer is in
   the cache (0 instructions on the steady path); the `bufq_map` check sits on the miss path.
5. **`tune.buffers.reserve`**: per-thread emergency buffers taken at thread start, the limit
   raised by `nbthread × reserve`, refilled first on give, the `q * reserve / 3` gate on queues
   1-3. The load-time refusal goes only when this reaches the take path.
6. **Deviations kept, for `docs/differences.md`**: Ibex serves a queue FIFO (HAProxy's observed
   order is an artefact of its retry pass); Ibex's CLI never waits for a buffer; a waiter whose
   client left is unlinked when the engine sees the close (epoll `RDHUP` needs no buffer), where
   HAProxy forwards its request later and logs `400 CH--`; Ibex does not reproduce the
   `stconn.c:1027` crash.

Order of the work (S6 §2): the queue type and its tests in `buf.rs`; the `MuxRx` site (the
task's acceptance test: under `limit 8` the connection past the limit waits and is served when a
buffer frees, not 500); then `SeRx`/`MuxTx` (no more `ID--`); then the reserve.
