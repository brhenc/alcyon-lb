## 0. Short answers

| Question | Answer |
|---|---|
| How many pools does HAProxy declare? | **119 distinct pool names** in `src/` + `addons/` [S] (DECLARE_*_POOL, create_pool, create_aligned_pool; `caphdr`/`ptrcap`/`sticktables` are one name each but one registration per config line). 30 of the names are QUIC/H3 (not built here), 4 Lua, 2 promex. This binary with the blog config of §6 registers **76 pools with `-dMno-merge`** and **71 after merging** (default) [M]; tradeoff.md's "69" was the bare config. |
| Does HAProxy pre-allocate its pools? | **No, except buffers.** Pools grow on demand with `malloc`/aligned alloc and keep what they got (per-thread cache up to `tune.memory.hot-size`, 512 KiB; the global shared cache is **off** by default, `-dMhelp` marks `no-global`) [M][S]. At start only `minavail-1` = 2 buffers are taken and returned to the pool (`dynbuf.c:76-81`) plus `tune.buffers.reserve` (default 4) **emergency buffers per thread** held outside the pool (`dynbuf.c:274-293`) [S]. So HAProxy's "0 malloc per request" is a **steady-state** property after warm-up, not "no malloc after start-up". The user's long-term goal goes beyond HAProxy. |
| Does HAProxy ever malloc on the request path? | Yes, a few documented exceptions (§2.6). Measured today with the blog config (`http-request set-var(txn.path) path`): **2 malloc + 2 free per request, 7-11 bytes**, plaintext, keep-alive and close alike: the variable's name (`vars.c:673`, `my_strndup`) and value (`vars.c:746`) [M][S]. With TLS (OpenSSL 3.5, `SSL_MODE_RELEASE_BUFFERS`, `ssl_sock.c:4140`): **9 malloc / ~50 KB per keep-alive request** and **714 malloc / ~458 KB per new TLS connection** [M]. Ibex+rustls today: 3 per TLS request, ~137 per handshake (plan-2100 §2.1) -- already below HAProxy+OpenSSL on TLS. |
| What does HAProxy do when a pool is empty? | It mallocs. When that fails (or a pool `limit` is reached; only buffers have one, `tune.buffers.limit`), `pool_alloc` returns NULL and the **caller fails just that object**: buffers fall back to an emergency buffer, else the task is **queued on the per-thread buffer wait list and woken when a buffer is freed** (`dynbuf.h`, `__offer_buffers`); other objects fail the stream/connection (`SF_ERR_RESOURCE`, termination flag `R`). SSL_new failure runs `pool_gc()` and retries once (`ssl_sock.c:6067-6100`). Never an abort [S]. |
| Ibex today | Real pools: I/O buffers (`buf.rs`, 64 spares/thread), the session arena (`engine.rs:1915`, pre-sized to maxconn), applet arena (`applet.rs:1875`), task arena (`ibex-sched/src/task.rs:263`), check-run box pool (`check.rs:285`). Everything else is `Box`/`Vec`/`String`/`HashMap` per object. Shipped binary: 2 / 5 / 62 mallocs per request (bare min / bare HTTP/1.0 ka / blog), pins in `harness/malloc_per_request.py:45-49` [S]. |
| Top recommendation | Do **not** port 119 pools one-for-one. Port **the mechanisms** (typed pool with per-thread cache and fallible take; fixed-size chunk pools sized from config; per-thread trash chunks; buffer wait queue + emergency reserve) into `ibex-alloc`, then move the ~20 objects that a blog's request path or an attacker can make allocate (§3.2). Many HAProxy pools have no Ibex object at all (stconn, sedesc, sockaddr, mux_pt...) because Ibex inlines them in `TcpSession` -- that is already a "pool chunk" (the session arena slot). |

## 2. How HAProxy avoids malloc beyond the pools

### 2.1 Pool mechanics (src/pool.c, include/haproxy/pool.h) [S]

- **Take** (`__pool_alloc`, pool.c:1027): per-thread cache first (`pool_get_from_cache`, pool.h:305;
  hottest object first, `-dMcold-first` reverses), then the shared global free list if enabled
  (`pool_refill_local_from_shared`), then the OS (`pool_alloc_nocache` -> `pool_get_from_os_noinc`,
  pool.c:524, which refuses when `pool->limit` is reached and increments `failed`). Returns NULL
  on failure: **callers check**. `POOL_F_NO_FAIL` exempts a call from `-dMfail`; `POOL_F_MUST_ZERO`
  zeroes (`pool_zalloc`).
- **Return** (`pool_put_to_cache`, pool.c:793): into the thread cache (LIFO per pool, plus a
  per-thread LRU across pools). If the thread's cached bytes exceed 3/4 of
  `tune.memory.hot-size` (default `CONFIG_HAP_POOL_CACHE_SIZE` = 524288, defaults.h:577), the
  pool's own oldest objects are evicted when it holds `>= 16 + count/8 + cluster`; above 100% the
  oldest objects of all pools are evicted (`pool_evict_from_local_caches`, pool.c:762).
  Evicted objects go to the shared list if `-dMglobal`, else **straight to `free()`**.
- **Merging**: pools with the same size (rounded) and compatible flags share one head unless
  `-dMno-merge` or `MEM_F_EXACT` (buffers, trash) [S]; printed `[SHARED]` with `users` = registrations [M].
- **No shrinking on a timer.** Memory goes back to libc only through cache eviction, `pool_gc()`
  (frees everything above `minavail` in every pool, then `malloc_trim(0)`; pool.c:974) on
  SIGQUIT-style dumps, soft-stop (haproxy.c:873), pause (haproxy.c:887), SSL_new failure
  (ssl_sock.c:6074-6099) and proxy stop (proxy.c:3715), and `no-memory-trimming` disables the
  trim [S]. Measured yesterday: allocated counts flat after 30 s idle (pools report §1.6 (e)).

### 2.2 Pre-allocation at start [S]

| Mechanism | What it pre-allocates |
|---|---|
| `init_buffer` (dynbuf.c:30-83) | `minavail = MAX(tune.buffers.reserve, 3)`; allocates `minavail-1` buffers with `pool_alloc_nocache` and frees them into the pool (so 2 buffers exist before traffic). Sets `pool->limit = tune.buffers.limit` when non-zero. |
| `alloc_emergency_buffers_per_thread` (dynbuf.c:274-293) | `tune.buffers.reserve` (default 4) buffers **per thread**, outside the pool, raising `limit` by one each so they don't count. |
| trash, logline | 3 x bufsize trash per thread (`chunk.c:204-212`), log buffers per thread (`log.c:3952`). |
| cache, ssl session cache, stick tables' shared parts, rings | shared-memory / big blocks at start (`shctx`, ring storage `ring.c:92`). Stick-table **entries** are pooled on demand, bounded by `size`. |
| `prealloc-fd` (cfgparse-global.c:902; limits.c:548) | Not memory: dup2's the highest fd once so the kernel's fd table is grown at start rather than on the first accept beyond it. |
| `maxconn` sizing (limits.c:280-330) | No allocation: with `-m <MB>` (`global.rlimit_memmax`) and TLS, maxconn is computed as `mem*0.97 / (STREAM_MAX_COST + 2*bufsize + sides*ssl_session_max_cost + ssl_handshake_max_cost)` (`STREAM_MAX_COST` defaults.h:539). `-m` also sets `RLIMIT_DATA` (limits.c:501-518), so a malloc beyond it fails (NULL) instead of the OOM killer. |

Nothing else is pre-allocated: `stream`, `session`, `connection`, `h1s`... appear on first use [M]
(start snapshot: `stream` 1, `session` 1 = the CLI session querying, `http_txn` 0).

### 2.3 When no buffer is available: the wait queue [S]

`b_alloc(buf, crit)` (dynbuf.h) with a criticality `enum dynbuf_crit` (dynbuf-t.h:57-65):
`DB_GROW_RING`, `DB_UNLIKELY` (L7 retries), `DB_MUX_RX`, `DB_SE_RX`, `DB_CHANNEL`, `DB_MUX_TX`,
`DB_PERMANENT`. Four per-thread queues (`th_ctx->buffer_wq[]`, map `bufq_map`):

1. `b_may_alloc_for_crit` refuses when a queue of the same or higher criticality is non-empty
   (no queue jumping) or when emergency buffers are below the class's share (q3 0%, q2 33%,
   q1 66%, q0 100% of reserve).
2. Else `pool_alloc(buffer)`; on NULL, take an emergency buffer.
3. On failure `b_alloc` returns NULL, `activity[tid].buf_wait++`; the caller registers a
   `struct buffer_wait { target, wakeup_cb, list }` with `b_queue(crit, bw, ctx, cb)` (crit below
   `DB_MUX_RX` is never queued and just fails) and returns; e.g. the stream sets
   `SF_ERR_RESOURCE`-free waiting state, the h1/h2 mux stops reading.
4. `b_free` refills emergency buffers first, then returns to the pool, then `offer_buffers(from, n)`
   wakes up to `n` waiters in criticality order (`__offer_buffers`, dynbuf.c:129-158; the
   callback returns 0 if it does not want the buffer any more).

Effect: a buffer shortage **slows** streams down instead of failing them; with
`tune.buffers.limit` set the documentation warns waiting tasks "may freeze until their timeout
expires" (configuration.txt `tune.buffers.limit`). A stream that cannot get a buffer before its
timeout ends on its timeout, not on an allocation error.

## 4. Port design for Ibex (safe Rust)

Constraint recap: `ibex-rt`, `ibex-proto`, `ibex-sample`, `ibex-sched`, `ibex-tls`... are
`#![forbid(unsafe_code)]`; `ibex-alloc` has local `#[allow(unsafe_code)]` (lib.rs:154, :618) and is
where any unsafe goes (its header comment lib.rs:10-11 claims `forbid` and mentions a `Pool` type
that does not exist: fix the comment in P0). Dependencies must be pure Rust (memory note).

### 4.1 Typed pools: `ibex_alloc::Pool<T>` (P0, Opus)

Two forms, both already proven in the tree, generalised:

1. **Index arena** (what `SessionArena`, `TaskArena`, `AppletArena`, stick-table slots do): a
   `Vec<Slot<T>>` pre-sized at start, free list of `u32`, handles instead of pointers, generation
   counter in the handle to catch stale use. Safe, no unsafe at all. Use for objects owned by an
   engine/thread and referenced by index (sessions, H2 streams, idle conns, stick entries).
   Extract the common code into `ibex_alloc::Arena<T>` (currently three hand-written copies:
   engine.rs:1915, applet.rs:1875, ibex-sched task.rs:263).
2. **Box recycler** (what `buf.rs` THREAD_POOLS and `check.rs` RUN_POOL do): `PoolBox<T>` = a
   `Box<T>` that on `Drop` resets the value and returns the box to a **per-thread cache**
   (`thread_local!` `RefCell<Vec<Box<T>>>`), falling back to a **shared** `Mutex<Vec<Box<T>>>`
   only when the object moved threads (H2 children on another worker are not a thing today, but
   idle server conns and stick entries can cross). Use for objects that are moved around or
   type-erased (TLS contexts, H2 mux contexts, queue waits).

Common API (sketch):

    pub struct PoolSpec { name: &'static str, size: usize, align: usize, file: &'static str, line: u32 }
    pub struct Pool<T: Reset> { spec, counters: PoolCounters, cache: LocalKey<..>, limit: AtomicUsize }
    impl<T: Reset> Pool<T> {
        pub fn try_take(&'static self, init: impl FnOnce() -> T) -> Result<PoolBox<T>, PoolFull>; // cache, else grow (fallible), else Err
        pub fn prefill(&'static self, n: usize) -> Result<(), PoolFull>;                         // start-up
    }
    macro_rules! declare_pool { ($vis static $NAME: Pool<$T>, $name:literal) => { .. register in the registry with file!/line!() .. } }

- **Fallible growth** is the one place that needs unsafe: `try_box<T>(v: T) -> Result<Box<T>, T>`
  in `ibex-alloc` (`std::alloc::alloc(Layout::new::<T>())`, null check, `ptr::write`,
  `Box::from_raw`; ~15 lines, Miri-tested). For byte buffers no unsafe is needed:
  `Vec::try_reserve_exact` (stable) then `resize`, as plan-2100 Z4 says.
- **Counters** = HAProxy's: `allocated`, `used`, `cached` (per-thread, summed on dump),
  `needed_avg` (the swrate HAProxy keeps: `swrate_add_scaled_opportunistic`, pool.c:572 -- implement
  the same sliding average, today Ibex prints 0), `failures`. Relaxed atomics, no lock on take/return.
- **Per-thread cache budget**: `tune.memory.hot-size` (default 524288) with HAProxy's eviction rule
  (3/4 and 100% thresholds, pool.c:813-822). Evict = return to the shared list (Ibex policy), not
  `free()`, when the "no allocation after start" mode is on (§4.5).
- **Registration**: `declare_pool!` registers a `PoolStatsFn` with the existing `PoolRegistry`
  (lib.rs:287) and its `PoolReg{file,line}` so `show pools detailed` shows the Rust site, as
  today for buffers. Merging (`[SHARED]`) is not reproduced: every Ibex pool is exact; print
  `users 1` and no `[SHARED]` except where Ibex genuinely shares (the buffer pool serving TLS raw
  buffers would print 2 users -- that is honest).

### 4.2 Chunk pools: `ChunkPool` (P1)

HAProxy's `requri`, `capture`, `caphdr`, `uniqueid`, `ssl_sock_client_sni`, `hpack_tbl`,
`pp_tlv_*` are untyped fixed-size byte pools whose size comes from the config. Ibex equivalent:
`ChunkPool { size }` handing out `Chunk` = `PoolBox<[u8]>` + `len`, with `as_str()` (bytetext
rules as tradeoff §6.12) and `push_truncating(&[u8])` (HAProxy truncates captures at their length,
never grows). Size classes created at config time, one per distinct length (Ibex does not merge;
`show pools` lists `caphdr` once per length, as HAProxy's `-dMno-merge` does). A `Chunk` never
reallocates: a write past `size` truncates, exactly HAProxy's semantics for captures and `%r`
(1024 by default, `tune.http.logurilen`).

### 4.3 Trash (P1)

    thread_local! { static TRASH: RefCell<TrashSet> }   // N chunks of bufsize, filled at thread start
    pub fn with_trash<R>(f: impl FnOnce(&mut Chunk) -> R) -> R  // borrows one, returns it after f
    pub fn alloc_trash_chunk() -> Result<PoolBox<Chunk>, PoolFull> // pool "trash", like HAProxy

HAProxy's two rotating buffers rely on "valid until the next-but-one call", which Rust cannot
express safely. The closure form gives the same zero cost with a checked lifetime; nesting
(a converter calling a fetch) takes the next chunk of the set (`TrashSet` of 4, a `RefCell`
borrow panic is impossible because each level takes a different index; if all 4 are in use the
5th level falls back to `alloc_trash_chunk`, which is a pool take). The per-thread **log buffer**
is one more chunk of `max_syslog_len` (`log.c` logline). `truncate_to_trash`
(ibex-sample registry.rs:6494) becomes "the chunk is bufsize, a write truncates" -- the same
observable result as today. Sample values (Z7b) can then be `Sample::Str(TrashRef)`/borrowed
`&str` within one rule evaluation; that is the design decision Z7b already defers to Opus.

### 4.4 Buffer wait queue and emergency buffers (P2, extends Z4)

Port HAProxy's semantics, not "fail the stream" (which plan-2100 Z4 chose for M1):

- `Buf::try_alloc(crit: BufCrit) -> Result<(), BufWait>` with `BufCrit` = HAProxy's seven
  criticalities and the same queue mapping (`DB_CRIT_TO_QUEUE`, dynbuf-t.h:88) and the
  emergency-share rule of `b_may_alloc_for_crit`.
- Per-thread `BufWaitQueues { q: [VecDeque<TaskRef>; 4] }` -- **pre-sized to maxconn** at start
  (a waiter is a session, at most one entry each), so queueing never allocates. `Buf` drop
  (buf.rs:429) refills the reserve first, then the cache, then wakes up to one waiter per freed
  buffer through `Scheduler::wakeup` (sched.rs:391).
- A waiting session stops reading (its I/O interest cleared) and is woken with a new wake reason;
  its timeouts keep running, so a long shortage ends on `timeout client/server` as in HAProxy.
- `tune.buffers.limit` (>= 0, 0 unlimited) and `tune.buffers.reserve` (default 4) with
  HAProxy's parsing (dynbuf.c:161-204). Counted in `show activity`-style counters (`buf_wait`)
  and `show pools` `failures` when the OS refuses.
- Objects other than buffers (session slot, TLS ctx, h2c) do not queue in HAProxy either: on
  `PoolFull` the connection is refused (accept path: HAProxy's static 500 on HTTP listeners,
  session.c:397-420) or the stream ends with `R`.

### 4.5 Sizing at start-up, and "no allocation after start"

HAProxy does not do this (§2.2); it is the user's long-term goal. Proposed policy knob (Ibex
extension, refused by name in nothing HAProxy accepts): **`tune.memory.prealloc <percent>`** or
simpler two modes -- this is open question Q1:

- **grow (default, HAProxy parity)**: pools start empty (buffers: 2 + reserve), grow fallibly on
  demand, never shrink except by the hot-size eviction and `pool_gc` events. Steady state = 0
  malloc after the first peak.
- **fixed**: at start, each pool is filled to `count = f(maxconn, nbthread, config)`, e.g.
  session slots = maxconn, buffers = `2*maxconn` capped by `tune.buffers.limit`, h2c =
  maxconn x (h2 binds?), h2s = maxconn x `tune.h2.max-concurrent-streams` capped... and growth is
  disabled: an empty pool is `PoolFull`. Needs a realistic maxconn: HAProxy's automatic maxconn
  here was 524274 (from `ulimit -n`) [M], which at 2 buffers each is 17 GB -- impossible, so
  "fixed" must require an explicit `maxconn` or `-m`, and `-m` (Ibex: a maxconn budget, commit
  cab9bf4b) becomes the natural input: `maxconn = mem / per-connection cost` exactly as
  limits.c:303-330 computes it, then pre-fill.

Either way the start-up allocation stays allowed and outside the measured window (plan-2100 §2.2).

### 4.6 Allocation failure must not abort

Every runtime take is `try_*` returning `Result`; the compiler finds the callers. What remains
infallible (rustls, quinn-proto internals, `Vec::push` past capacity anywhere) still aborts on
OOM: T357 (panic and allocation-failure hardening) owns that list. The proof test for the end
state is HAProxy's own: **`-dMfail` / `tune.fail-alloc`** -- Ibex can implement it in the pools
(random `PoolFull` at rate N%, `POOL_F_NO_FAIL` for the emergency reserve) and a test runs traffic
under `tune.fail-alloc 5` expecting only `R`/500 failures and a live process. Today `-dM` is
refused (T351) because there were no pools; it becomes implementable after P0.

### 4.7 How `show pools` reports them

- Each `declare_pool!`/`ChunkPool`/arena registers a provider (registry exists, lib.rs:306).
- Names: use HAProxy's names where the object corresponds (`session`, `stream` is not a separate
  Ibex object -> do not invent it; `trash`, `buffer`, `requri`, `caphdr`, `uniqueid`, `h2c`,
  `h2s`, `hpack_tbl`, `ssl_sock_ctx`, `pendconn`, `sticktables`, `task`), Ibex names where there is
  no counterpart (`tls_raw` if not merged into `buffer`). Sizes are `size_of::<T>()` and will differ
  from HAProxy's -- that is expected and was already accepted for `session`.
- `needed_avg` (sliding average) and `failures` become real numbers.
- `show info`: `PoolAlloc_*`, `PoolUsed_*`, `PoolFailed` already exist (cab9bf4b); add the
  non-pool heap count from the shipped-binary counter as an Ibex extension only if the user wants
  it (Q4).

### 4.8 Composition with what is merged

- Z1 (`harness/malloc_per_request.py` + `tools/allocshim`) stays the acceptance oracle: every slice
  below lowers a pin there first (failing-first, rule 1), and `request_allocations.rs` pins in
  process.
- Z2 (parser on the stack) done. Z3, Z5, Z6, Z7 (BORROW work) stay as planned: they remove
  allocations a pool cannot (variable-size copies). Z4 is extended by P2 (wait queue rather than
  fail).
- `buf.rs` keeps its API; its `THREAD_POOLS` becomes an instance of `Pool` (P0 migrates it so
  there is one mechanism).
- `trim_idle` (buf.rs:287), `SessionArena::trim_tail` (engine.rs:2005) and the
  back-to-baseline leak test (`mixed_traffic_returns_to_baseline`, commit fc6f0c14) **conflict**
  with "no allocation after start": they give memory back after a burst so the next burst
  mallocs again. HAProxy does not shrink. Q2.

## 7. Open questions for the user

- **Q1 Grow or fixed?** HAProxy grows pools on demand and keeps them (0 malloc only after warm-up).
  "No allocation after start-up" needs fixed pre-sized pools, which needs an explicit `maxconn`
  or `-m` (auto maxconn here is 524274). Default to HAProxy's grow-and-keep, with a fixed mode as
  an opt-in? Or fixed by default?
- **Q2 Shrinking.** `trim_idle`, `SessionArena::trim_tail` and the back-to-baseline leak test
  (merged 10-17) give memory back after a burst; that makes the next burst malloc again and
  differs from HAProxy (flat after the burst). Keep them (operator sees RSS return), drop them
  (soft-realtime), or keep only for the grow mode?
- **Q3 Buffer shortage: wait (HAProxy) or fail the stream (plan-2100 Z4 M1)?** This spec
  recommends wait, as HAProxy, with the queue pre-sized so waiting cannot allocate.
- **Q4 Beyond HAProxy?** HAProxy mallocs for `set-var`, error snapshots, pattern LRU, Lua,
  inside OpenSSL. Should Ibex hold itself to 0 there too (P7 vars, and rustls's per-record
  allocations via its unbuffered API), or match HAProxy's exceptions and document them?
- **Q5 Names in `show pools`.** Use HAProxy names only where the object really corresponds and Ibex
  names otherwise (this spec's proposal), or force HAProxy's list for script compatibility?
