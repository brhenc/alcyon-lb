# Why Alcyon copies: ownership, lifetimes and where the bytes live (T610, 2026-11-02)

Status: design, no code. Branch fix/t610 from main c8949446 (X8 merged; O1b on fix/o1b, not
merged). Inputs: `tasks/{X4,O1a,R2,R4,X7,X8}-design-notes.md`, `fix/o1b:tasks/O1b-design-notes.md`,
C-X1..C-X6, C599, the three design docs named in the task, HAProxy 3.5-dev (`src/mux_h2.c`,
`src/h2.c`, `src/hpack-dec.c`, `src/h3.c`, `src/stream.c`), and the profiles in §5 (this branch
= main, release-perf with frame pointers and line tables, `ibs_op` on slot B, two sampling
periods per scenario). "k" is 1,000 user instructions a request; a figure "a / b" is the two
captures (period 100,000 / 20,000), both scaled to the insreq user total.

## 0. Short answers

1. **The task's premise is half right.** HAProxy does *not* have the stream before it decodes
   HEADERS. `h2c_frt_handle_headers` (mux_h2.c) calls `h2c_dec_hdrs` first: HPACK into a stack
   `list[]` plus the trash chunk, then `h2_make_htx_request` into a **buffer allocated for a
   stream that does not exist yet** (`h2_get_buf(h2c, rxbuf)`); only then `h2c_frt_stream_new(h2c,
   id, &rxbuf, flags)` (mux_h2.c:2169) makes `h2s`, `sc` and `stream`, taking the buffer by value,
   and `h2_rcv_buf` (mux_h2.c:8043) later **swaps** it into the channel (`b_xfer` of the whole
   buffer when the channel is empty). h3 is the same (`h3_req_headers_to_htx` h3.c:706:
   `qpack_decode_fs` into `list[]`/`tmp`, `b_alloc(&htx_buf)`, `htx_add_*`, then `qcs_attach_sc`).
   What HAProxy has is not "the owner exists first" but **"the intermediate is already the
   final representation, in memory that moves by swap"**. That is the change Alcyon needs, and it
   is far cheaper than moving streams into their owners.
2. **Two structural changes remove most of the table.** (A) The h2/h3 mux writes the request
   head as HTX blocks into a pooled buffer that becomes the stream's `htx_buf` by a move:
   `H2ReqHead`, `put_request_head`'s h2 use and `finish_request_head` go, one write instead of
   three. Deleted, measured: **2.5-4.7k on h2s1, 2.2-2.6k on h3** (§5); expected net **-2 to
   -3k h2s1, -1.5 to -2k h3fit**. (B) The request phase borrows the session by parts (`ReqView`
   by destructuring, one `SampleContext` per phase, no `mem::take` of the vars, no
   `res_caps.clone()`): deleted 0.7-0.9k on rules, expected **-0.5 to -0.8k**; its worth is
   that X3b's response rules and the vars-as-bytes work land on the same shape.
3. **The response side is the bigger prize and X3b already owns it**: on rules the list build +
   its spares + the text written back + the facts walked twice are **5.6-7.5k**; on h2backend
   the h1 text the h2 codec writes and the parse of it are **4.9-7.7k** (§5). X3b stays, reshaped
   to write blocks with A's writer (§6).
4. **O1c as "streams held by the owner" is not worth building.** O1b measured the object at
   ~1-1.5k and parked it (-572 h2s1). What a `Vec<Stream>` in the owner would still remove is
   `get2_mut` + the stale-task checks (0.07-0.14k measured), `Scheduler::create` (0.02-0.04k),
   two 1.6 KB moves (~0.1k). The cheapest correct route to the rest is three in-place fixes
   inside the arena (§4): **-0.5 to -0.9k**. No handles, no take/put per run. The h3 gap is
   quinn and the listener's serve path (§5.2), not the stream object.
5. **Estimates are attributed instructions of the functions a change deletes**, from the §5
   profiles, less what the replacement must still do (stated per row). No operation counts.

## 1. The copies, in ownership terms

The pattern is the same everywhere: a value is produced by code that owns memory of the *wrong
lifetime* (the connection's, the thread's, a temporary) because the right owner (the stream)
cannot be borrowed at that point, so the value goes into an owned intermediate and is copied
again when the right owner is reachable. Per copy: who owns the bytes at each step, whether the
final owner exists then, the borrow that blocks, HAProxy's arrangement, the measured cost.

## 2. What HAProxy does with the head (source, for the record)

```
h2c_frt_handle_headers(h2c)                           mux_h2.c
  rxbuf = BUF_NULL
  h2c_dec_hdrs(h2c, &rxbuf, &flags, &body_len)
    tmp = get_trash_chunk(); list[tune.max_http_hdr*2]  trash chunk + stack array of {ist n, ist v}
    h2_get_buf(h2c, rxbuf); htx = htx_from_buf(rxbuf)   the stream's future buffer, from the pool
    hpack_decode_frame(ddht, hdrs, flen, list, tmp)     hpack-dec.c:151: ist into the frame or the
                                                        table; huff_dec copies into tmp only
    h2_make_htx_request(list, htx, &msgf, body_len)     h2.c:323: htx_add_header per field
  h2s = h2c_frt_stream_new(h2c, id, &rxbuf, flags)      mux_h2.c:2169: h2s_new, sedesc_new,
                                                        sc_new_from_endp(sd, sess, input = rxbuf)
h2_rcv_buf(sc, buf)                                     mux_h2.c:8043: channel empty and it fits:
                                                        b_xfer of the whole buffer (a swap)
```

Two copies (tmp for Huffman only; `htx_add_header`), none after the stream exists; `h2c_dec_hdrs`
3.2k + `h2_make_htx_request` 2.6k on h2s1 (engine doc §2.1 row 10). Alcyon, same request:

```
H2MuxContext::process_decoded_block                   mux_h2.rs:1654  (4.1 / 5.4k incl)

  dispatch_next(h2)                                   head = req_head.take(); walks; %r format!
```

The difference is not *when* the stream exists. HAProxy's intermediate **is** the HTX in a
buffer that moves; Alcyon's is a private struct that must be copied out, then checked again.

## 3. The two structural changes

### 3.1 A: the mux writes the head into the buffer the stream will own

**Shape.** `H2StreamCtx` and `H3StreamCtx` get `rx_head: Option<RxHead>`: a pooled byte buffer
in the X1 layout (`HtxSlice` over it: payload from the front, 16 B descriptors from the back),
from a per-thread `alcyon_alloc::Pool` of the small class (AGENTS §8; `alcyon-proto` already depends
on `alcyon-alloc`; `Buf.data` is a `Box<[u8]>`, so `Buf::adopt(RxHead)` moves the box, no copy).
`H2ReqHead::write` becomes `write_request_htx(fields: &DecodedFields, out: &mut HtxSlice,
relaxed) -> Result<HeadFacts, &'static str>` in `alcyon-proto` (`h2.rs`, beside
`check_request_fields`, which folds into the same pass as in `h2_make_htx_request`): the same
pseudo-header rules in the same order as today's `write` + `put_request_head` (`:method`,
`:path`, `:authority`, `:scheme`, `:protocol`; duplicates and order; `host` from `:authority`
where HAProxy puts it; the extended-CONNECT `upgrade`/`connection: upgrade` pair; one canonical
`content-length`; the `too_many`/`too_big` limits counted as it writes), writing `ReqLine` +
`Header`... + `Eoh` into `out` and collecting what `finish_request_head` recomputes today
(`seen` bits, host index, line count, `field_bytes` for `%U`, `ext_connect`, method/URI spans,
the content-length). `HeadFacts` (a few words) sits on the stream ctx.

`dispatch_next`/`dispatch_mux` return `H2Dispatch { rx: RxHead, facts, .. }` (no
`Box<H2ReqHead>`); `start_request` does `sess.htx_buf = Buf::adopt(d.rx)` and sets
`htx_tail`/`htx_blocks`/`has_htx`/`htx_modified`/`req_head_pending` from the facts; `%r`'s line
and `req_method`/`req_uri` come from the spans. `give_back_head`, `spare_heads`, `H2ReqHead`
(61 references: `h2_bridge.rs` 32, `mux_h2.rs` 11, `mux_h3.rs` 9, `htx_mux.rs` 4, `engine.rs`
4, `htx.rs` 1), `put_request_head`'s h2 caller (4 callers in all), `finish_request_head`'s h2
use, `h2_head_size`, `wire_len`, `text_headers` (2 callers) go.

The pool: the engine owns it (one per worker, as `buffer`'s `THREAD_POOLS`) and hands the mux
spares through the channel `spare_htx` uses today (`spare_rx: Vec<RxHead>`, refilled before
`handle_frame`); a decode with no spare refuses the stream (`RST_STREAM REFUSED_STREAM`, the S5
`fail_alloc` path), never a malloc on the path. A stream reset before dispatch gives its
`RxHead` back. `show pools` counts them with the small `buffer` class.

**What it removes, measured** (§5.1-5.2): copy 2 `H2ReqHead::write` 0.83 / 1.67k (h3 0.38 /
0.50k), copy 3 `put_request_head` 2.66 / 1.47k (h3 1.6 / 1.4k), the `dispatch_next` walks 0.31 /
0.17k (h3 0.4-0.5k): **deleted 2.5-4.7k on h2s1, 2.2-2.6k on h3** (the four extra field passes
in `process_decoded_block` go too, not separately attributed). **What it keeps:** one write of
the same bytes as blocks, which is what `write` does today into `bytes` with 16 B descriptors
in place of 12 B spans: bounded by `write`'s own byte-copy share (self 0.37-0.59k + its share of
`memcpy`), **<= 1k**; the oracle's `h2_make_htx_request` is 2.6k for the same job and Alcyon's
must stay under it. **Net expected: h2s1 -2 to -3k, h3fit -1.5 to -2k** (h3 raw, see §5's
scale note); keepalive/rules 0 by construction (no h1 code touched); kernel 0. Stop rule: under
-1.5k measured on h2s1, stop and report.

**Why it is safe.** Memory safety unchanged: an owned `Box<[u8]>` moved by value, the
`HtxSlice` view borrows it for one call, no `unsafe`, no refcount, one owner (AGENTS §8).
HAProxy behaviour: the block order and the refusals are the ones `H2ReqHead::write` +
`put_request_head` encode today, pinned by `h2_bridge::tests::the_htx_written_from_the_fields_is_
the_parsers_of_the_text`, the E1 rows (`h2_field_validity.rs`), T437/T449/T451 and
`h3_request_framing_to_backend.rs`; S1 adds the differential row "`write_request_htx` over the
T15/E1 corpus equals `write` + `put_request_head`" before S2 deletes the old path.

**What it does not do.** Copy 1 (`DecodedFields`) stays: HAProxy has the same (`list[]`/`tmp`)
and it is 0.2-0.3k here. Copy 4 stays for h1 servers, as in HAProxy. `req_method`/`req_uri`
stay as text until the HTX outlives the response (X2 item 3; a method enum + the logged line,
S6).

### 3.2 B: the request phase borrows the session by parts

**Shape.** One `ReqView<'s>` built once per rule phase by destructuring `TcpSession`
(`let TcpSession { htx_buf, htx_blocks, strm, cli_xprt, .. } = sess;`): the `HtxSliceRef`,
`&strm.log` (captures, dates, unique id), `&strm.txn` (the body view), the connection facts
(`client_addr`, `fc_*`, `ssl_fc`, `so_*`, versions), and **not** `strm.vars`.
`SampleContext::for_request(&ReqView, &PhaseConsts)` replaces the 34 `make_ctx!` expansions
(engine.rs:13706 and its siblings) and is built once per phase, not per rule (C-X2 item 5). The
actions take `(&mut HtxEdit, &mut VarStore, &mut StreamLog)` as disjoint fields of the same
destructuring: `set-var` writes `strm.vars` directly (no `mem::take` + put back, engine.rs:14196
and 17919), the response rules read `res_caps` through the view instead of `res_caps.clone()`
(2 sites; O1a item 4), and an HTX edit invalidates the view by the borrow checker (`HtxEdit` is
`&mut` over the same `htx_buf`: a sample cannot live across it, HAProxy's "no sample across
`htx_defrag`" discipline enforced by the compiler). `htx_slice()`, `txn_req_body(&sess)`,
`sess_term_state(&sess)` become functions over the two or three fields they read, so the 18
`with_htx_mut`/`with_htx_synced` sites keep one live view per phase instead of a rebuild +
`note_htx` per edit (X4 §3).

**What it removes, measured** (§5.3, rules): `SampleContext` 0.17 / 0.29k, `htx_slice` +
`txn_req_body` 0.3-0.4k, the `with_htx_mut` rebuilds ~0.2k (`over_received_with` + `note_htx`),
the two swaps and clones (not attributable, small): **deleted 0.7-0.9k, net expected rules -0.5
to -0.8k**; keepalive ~0, h2s1/h3fit 0. The X0 figure of 2.11k for the contexts is gone since
X2; B's own saving is small. **Its worth** is structural: X3b's response rules take the same
`ResView` shape (no thread-local list), the vars can hold bytes without a swap (S6), and C-X2
item 1 (descriptors in `sess.req`) retargets one view type. **Cost to build:** the 34 sites and
the free functions X4 §3 names (`rewrite_request_connection`, `write_pending_head`'s three-field
read, `H2ReqBody::head_room`) in engine.rs's rules region and proxy.rs: mechanical once the view
exists; Opus for the borrow design; no behaviour change (rules battery, `htx_primary.rs`,
`request_allocations` pins green throughout).

### 3.3 Not proposed: streams inside the owner, handles with generations

O1b §1 lists why the owner-held `Vec<Stream>` was not built: 47 `self.sessions.*` sites (9
`get2_mut`), the scheduler's `WorkKind` 24-bit index, the fd table's task per server fd, the
child reaching its owner while it runs (the same `&mut` twice), the bridge taking both entries
whole. All true, and the measured prize is small: `get2_mut` 0.14 / 0.07k on h2s1 (0.07k h3),
`Scheduler::create` 0.04 / 0.02k, `SessionArena::alloc` 0.02k, the two 1.6 KB moves ~0.12k
(O1b). A `TaskRef` generation (alcyon-sched) would let a parked session keep its task (O1b §5),
a safety property worth having some day, not a per-request saving. Boxing entries to make moves
cheap costs the pointer load at ~300 sites (O1a: +0.3k keepalive). **The arena stays; O1b's
parking is the stream model.**

## 5. Profiles

Method: `cargo build --profile release-perf --bin alcyon` of this branch (= main c8949446) with
`RUSTFLAGS="-C force-frame-pointers=yes"` and `CARGO_PROFILE_RELEASE_PERF_DEBUG=line-tables-only`
(inlines expanded by `llvm-symbolizer`; frame pointers may shift inlining by ±100-200);
`tools/measure/slot.sh --wait` gave slot B (CPUs 12,13,14); `perf record -e
'ibs_op/cnt_ctl=1,swfilt=1/u' --call-graph fp -c 100000` (then `-c 20000`) over 10,000 requests
(h2s1, rules ab1) or 5,000 (h2backend ab1, h3best) after a 2,000-request warm-up; folded with
X0's `fold2.py`, kernel-leaf samples dropped, the rest scaled to the insreq user total of the X8
after-measurement (h2s1 53,781; rules 55,311; h2backend 121,425); h3best has no insreq figure
