## 0. Short answers

| Question | Answer |
|---|---|
| 1. Wire protocol | **HAProxyS 2.1**, one TCP connection per peer pair, text hello (3 lines) + status line, then 2-byte-class/type binary messages with a varint length for types ≥ 128. Captured and decoded in §5 and the vectors file: hello/`200`, resync-request/partial/finished/confirm, heartbeat (every 3 s idle, both ways, 5 s dead timer), table-define (id, name, key type/len, data bitfield, expiry, per-frqp period), update / inc-update / **update-timed / inc-update-timed** (teach only), ack. An Alcyon peer that sends exactly these, accepts a `2.0` hello by replying with 2.0 semantics (no heartbeat, no timed updates, `PEER_DWNGRD_MINOR_VER`), and applies the collision rule of §5.6 can sit in one `peers` section with HAProxy nodes in both directions. |
| 2. Config surface | Today Alcyon **refuses** the whole `peers` section, `stick-table … peers/nopurge/srvkey/write-to/recv-only/brates-factor`, `bind … shards`, global `localpeer` (generic unknown keyword) and does not parse `-L`; **`server … shard` is accepted and dropped** (AGENTS.md §5 defect, `server_keywords.rs:104`). M3 wires `peers` {`peer`, `bind`, `server`, `table`, `disabled`/`enabled`}, `localpeer`, `-L`, `stick-table … peers <name>`, `nopurge`, `tune.peers.max-updates-at-once`; it refuses by name `shards`/`shard`, `default-bind`/`default-server`, `log` in peers, `ssl` on peer binds/servers, `write-to`, `srvkey`, `recv-only`, `brates-factor`, `store server_key` (§2, §7). SSL to peers is a user decision (§10). |
| 3. Reload handover | The stopping process closes its remote sessions, connects **over TCP to its own local peer's bind address** (the `peer <localpeer>` / `bind` line; the local `server` line may not carry an address — measured: `'server A/A' : unknown keyword '127.0.0.1:62013'`), the new process answers the hello with `200`, sends resync-request, receives the whole table as `update-timed`/`inc-update-timed` (remaining expiry carried, measured `exp=592864` of 600000) and `resync-finished`, confirms; the old process exits within the second. **Measured condition:** the old process teaches only when its own resync state is `FINISHED` (`flags & 0x3 == 0x3`); a node that only ever got a `resync-partial` from its peer (two nodes started inside the same 5 s window) exits **without teaching**, and the new process learns from the remote peer after the 5 s local timeout (§4.3). Alcyon: master-worker `-sf` adds the same TCP teach step (§6.6); the socket handover (`handover.rs`) is untouched. A HAProxy old process can teach a new Alcyon process this way: that is the migration path. |
| 4. Multi-threaded sync | HAProxy: **one applet per peer session, pinned to the least-loaded thread at session creation** (`peer_session_create`, `applet_count[]`), one TCP connection per pair (a second session from the same peer kills the first: `release old session`, random 50-2050 ms reconnect delay), `process_peer_sync` on one thread. Updates from N request threads reach it through a per-thread-group `MT_LIST` → tasklet → one `eb32` update tree under `updt_lock` (write; the applet reads under a try-rdlock and gives up on contention). `shards` is **not** parallelism: it partitions keys across *different* peers (`server … shard k`; `ts->shard != p->srv->shard → skip`), for aggregators. **Measured:** at every rate this host could generate — 428k, 541k and 679k updates/s one way (16 and 32 sender threads), ~300k/s each way with both nodes serving traffic at ~62 % per thread — HAProxy **did not lag**: sender `localupdate − last_pushed` ≤ 6.3k (< 10 ms of updates), drained inside the next 1 s sample, receiver table complete. Cost: **0.8-1.0 µs of one receiver thread per update** (43-45 % of a core at 557-680k/s) and **+0.2-0.5 µs on the sender's applet thread**; a lag needs > ~1.2 M updates/s per peer pair or a sync thread starved by its own traffic (§4.4). Alcyon design (§6): one session per peer as the wire requires, placed on the least-loaded worker, **per-worker SPSC dirty rings** feeding it (the request path writes one slot in its own ring; no lock, no atomic RMW), an update sequence per table, ordering and acks as HAProxy's, no update lost (the dirty set is bounded by the table: one `seq` per entry, coalesced). Exit criterion proposal in §3 (the task's "where HAProxy lags" cannot be anchored on this host; see §10 decision 5). |
| 5. What exists in Alcyon | `crates/alcyon-stick-table`: one `RwLock<StickTableInner>` per table (no buckets), `update_entry` takes the **write lock on every tracked request** (`engine.rs:16345`, `6420-6529`, `7120-7404`), entry ≈ 600 B (`StickEntryData`, 10 `Option<SlidingRate>`), no update sequence, no dirty mark, no `Pool`; `show table` only (no `clear`/`set table`). Peers needs from it: a per-entry `seq: u32` + `flags: u8` (queued/seen) + `shard: u16` + two `u32` links for the per-table update list (≈ 16 B/entry, §6.7), bucketed locks (P0), and `apply_remote()` (§6.5). |
| 6. Topology and tests | Two Alcyon + one HAProxy in one section, a client alternating between the three, `sc_http_req_cnt`/`sc_gpc0` and stickiness agree on all three (script `tools/practical/08-peers/`, §8). ## 1. Scope (in)

1. **Wire compatibility with HAProxy 3.5 (protocol 2.1, 2.0 downgrade).** Hello/status, control,
   error, stick-table classes; all 27 data-type bits decoded (skipping what Alcyon does not store,
   including `server_key`'s dictionary encoding, which must be *parsed* to be skipped), 26 encoded
   (all but `server_key`); key types int/ipv4/ipv6/string/binary; `update-timed` on teach; heartbeat;
   collision rule; resync state machine (local 5 s → remote 5 s → finished), teach stage 1/2, acks.
2. **Config** (§7): `peers` section with `peer`, `bind` + `server` form, `table`, `disabled`/`enabled`;
   global `localpeer`, `-L`; `stick-table … peers <name>` on frontends/backends/listen; `nopurge`;
   `tune.peers.max-updates-at-once`; `-c` passes `reg-tests/peers/basic_sync*.vtc` configs.
3. **Data path**: every writer of a tracked entry (`track-sc*`, `sc-inc-gpc`, `sc-set-gpt`,
   `stick store`, request/byte accounting, `gpc_op`) marks the entry dirty in its own worker's ring;
   remote updates apply to the table and are visible to `sc_*` fetches and `stick match` at once;
   `write-to`-less semantics as HAProxy's (last writer wins per entry, counters are replaced, not added).
4. **Operations**: `show peers` (HAProxy's layout: section line, per-peer line, shared tables with
   `last_acked/last_pushed/last_get/update`), `show table` unchanged, reload teach through the local
   peer under `-W`/`-sf`, graceful stop closes sessions, `hard-stop-after` bounds the teach.
5. **Memory** per `memory-2026-10-24.md`: peer session, rx/tx buffers and the per-worker rings are
   `Pool`/`Arena` objects; nothing allocated on the request path; the dirty set is bounded by the
   table size.
6. **Verification**: unit tests from the captured vectors; `tests/it/peers_*.rs` against the oracle
   as the second node (both directions); the two non-TLS reg-tests `PASS`; `08-peers` topology; a
   night measurement (§3 rows); 24 h soak with sync traffic, RSS flat.

## 2. Refused (the parser names the keyword; each row is a gap-table row in §7)

- `shards` (peers) and `server … shard <n>`: aggregator partitioning; **today `shard` is accepted
  and dropped — slice P1 makes it refuse** (AGENTS.md §5).
- `default-bind`, `default-server`, `log` inside `peers`; `peers` `bind`/`server` with `ssl`, `crt`,
  `verify`, `ca-file` …: SSL peers (decision 1); `peer`/`server` with a unix or abns address (Alcyon
  peers are TCP/IP in M3; the local reload teach uses the bind's TCP address as HAProxy does).
- `stick-table … write-to`, `srvkey`, `recv-only`, `brates-factor`, `store server_key`
  (dictionary data type), `store gpt(n)/gpc(n)/gpc_rate(n)` *over the wire* only if P2's decoder
  finds the array encoding differs from the scalar one (decision 4 keeps them in if not).
- Several TCP sessions per peer pair (Alcyon-only extension): not until a measured lag exists (§10, 3).
- `peers` referenced by a `stick-table` in a `defaults` section, and `table` in peers with `type
  binary`/`len` > 64: HAProxy accepts both; deferred to the first user with a config that needs them.

## 3. Exit criteria (M1's shape)

- **Interop rows** (oracle as the other node, same host, each run 3×): (a) Alcyon → HAProxy and
  HAProxy → Alcyon: after 10 000 distinct keys × 5 requests on the sender, the receiver's `show table`
  equals the sender's (key set, `http_req_cnt`, `gpc0`, `http_req_rate` within one period) and
  `show peers` shows `last_pushed == last_get` on both; (b) teach: a restarted node (either binary)
  has the full table within 1 s of its hello, entries keep their remaining expiry (±1 s);
  (c) heartbeat: an idle pair stays `ESTA` for 10 min; a SIGSTOPped node is declared dead by the
  other after 5 s and reconnected within 5 s of SIGCONT; (d) collision: both nodes started together
  end with exactly one session per pair; (e) a 2.0 hello (`HAProxyS 2.0`) is served with 2.0
  semantics (verified against the oracle forced to `PEER_DWNGRD` by a scripted hello).
- **Throughput rows** (release build, night window, `flock`, muse paused, same config and traffic
  for Alcyon and HAProxy; relative): at the one-way load of §4.4 run 3 (32 sender threads, 100k keys)
  and the symmetric load of run 5, (i) **nothing lost**: receiver table equals sender table after
  the drain; (ii) **lag** (`localupdate − last_pushed` and sender − receiver `seq`) ≤ HAProxy's and
  drained within 1 s of the end of load; (iii) **CPU per update** on the sync thread (receive) and
  on the sender's extra thread ≤ HAProxy's measured the same night (today 0.8-1.0 µs / 0.2-0.5 µs
  on this host at load); (iv) the request path's instructions per request on `keepalive.body`
  with a `track-sc0` table *with* and *without* `peers` differ by ≤ 0.5 % (`insreq.sh`,
  release-perf, T518 rule); (v) `request_allocations` with a peered table: 0.
- **Reload row**: 100 master-worker reloads under constant `track-sc0` traffic from two clients,
  table size identical before and after each (±entries created during the teach), `show peers` of
  the new worker shows a local teach (`LOCALFINISHED`), 0 failed requests (today's reload tests'
  bar), old worker gone within `hard-stop-after`.
- **Reg-tests**: `basic_sync.vtc`, `basic_sync_wo_stkt_backend.vtc` → `PASS`; the two `tls_*` →
  `OUT_OF_SCOPE` with reason (or `PASS` if decision 1 is yes).
- **Topology** `08-peers`: 2 Alcyon + 1 HAProxy, same PASS table on all permutations of which node
  the client hits.
- **Robustness**: netfuzz slice on the peers listener (malformed hello, varint overflow, length >
  buffer, unknown class, table-define with keytype mismatch — the oracle enforces it since
  `1696cfaa1`), red-team pass, 24 h soak on `d13-test` with sync traffic, RSS flat, `show pools`
  shows the peers pools with `users` returning to baseline.
- **Documentation**: `differences.md` peers rows rewritten, `milestones.md` M3 → this file, the
  oracle defect of §4.5 recorded in `data/findings.csv` as an oracle row.

## 4. Measured findings

### 4.1 Wire capture, two oracle peers (relay 62011→62001 and 62012→62002)

`A.cfg`/`B.cfg`: `peers mypeers` with `peer A 127.0.0.1:62001`, `peer B 127.0.0.1:62012` (B reached
through the relay), `table t type string len 32 size 100k expire 10m store http_req_cnt,http_req_rate(10s),gpc0`,
frontend `http-request track-sc0 path table mypeers/t` + `http-request return`. Decoded by
`decode.py` (full file: vectors §V1):

```
0.481 >  HELLO 'HAProxyS 2.1\nA\nB 321273 1\n'            # B connects to A: proto ver, remote id, local id pid relpid
0.481 <  STATUS '200\n'
0.481 <  CTRL resync-request                             # both sides ask (both inside their 5 s local window)
0.481 >  CTRL resync-request
0.481 >  0a 82 10 01 02 2f74 06 21 f451 f0eda301 0a f0e203   table-define id=1 name='/t' keytype=6(string)
                                                         # keylen=33 data=[gpc0,http_req_cnt,http_req_rate] (0x604)
                                                         # expire=600000ms frqp=[http_req_rate/10000ms]
         00 02                                           # CTRL resync-partial (nothing to teach, not up to date)
0.481 <  (same define) ; CTRL resync-partial
0.481 <  CTRL resync-confirm      0.481 >  CTRL resync-confirm
2.483 >  0a 80 0d 00000001 03 2f6b31 00 01 01 01 00       update id=1 key='/k1' gpc0=0 http_req_cnt=1
                                                         # http_req_rate=(age 1 ms, cur 1, prev 0)
2.483 <  0a 84 05 01 00000001                             ack table=1 updateid=1
5.503 >  00 04   5.513 <  00 04                           heartbeat, 3 s after the last message, each way
```

Table name on the wire is the table id **minus the section name**: `mypeers/t` → `'/t'`
(`cfgparse-peers.c:550`, `id + prefix_len`); a backend's `stick-table … peers` is sent as the
backend name. Varint: `b0 < 0xf0` → value; else `v = (b0 & 0x0f)`, then 7-bit groups with the
continuation bit **0x80**, and the encoder subtracts 240 then 128 at each stage (exact inverse in
`decode.py::dec`; 600000 → `f0 ed a3 01`, 1540 → `f4 51`, 10000 → `f0 e2 03`). Update id and ack
id are **4-byte big-endian, not varint**; so is the expiry in timed updates. Frequency counters are
three varints: `now_ms − curr_tick` (age), `curr_ctr`, `prev_ctr`; the receiver rebuilds
`curr_tick = now − age`. String keys: varint length + bytes (no NUL); int keys 4-byte BE; ipv4/ipv6
raw 4/16 bytes; binary raw `keylen` bytes.

### 4.2 Collision, teach after restart, no acks during teach

Both nodes connect to each other at start (`c1` on each relay). The side that receives a hello for a
peer that already has a session answers `200` + resync-request and then **closes the new one**
(`peers.c:3119 release old session`), and the loser reconnects after `50 + rand % 2000` ms
(measured 0.75 s): one session per pair survives, and **updates flow both ways on it** (A's `/k1..3`
`>`; B's `/k9` `<`). Restarting B (vectors §V2): B's hello, `200`, B sends resync-request, A sends
in one 101-byte write: table-define, `update-timed id=4 expire=591407 key='/k9' …`, `update-timed
id=1 …`, `inc-update-timed …` ×2 (`0a 86`: no id, id = previous + 1), `resync-finished`; B answers
`resync-confirm` and **sends no ack for taught updates** (commit `590c5ff2e`). Expiry on the wire
is the remaining lifetime; the receiver caps it at its own table's `expire`.

Reading: HAProxy's single session thread **keeps up at every rate this host can produce**: the
receiver spends 0.8-1.0 µs of one thread per applied update (6.82 s / 8.36 M, run 3), the sender's
applet thread adds 0.2-0.5 µs per update on top of its share of frontend work, the in-flight window
stays under 10 ms, and `max-updates-at-once 200` plus the try-rdlock on `updt_lock` do not starve
it. Updates coalesce (run 3: 8.36 M messages for 10.2 M requests = 18 % merged: a touch while the
entry is queued and not yet `seen` re-uses the queue slot). Extrapolated (not measured): a lag needs
≈ 1.2-1.5 M updates/s on one pair, or a sync thread with less than ~45 % of a core left — on a node
already at 90 %+ CPU, which the task's "several frontend threads" case does not reach here. Wire
cost ≈ 20 B per update (16 B message + 8 B ack per batch, not per update): ≈ 11 MB/s at run 3.
`shards` was not measured: it partitions keys across *peers* (§0 Q4), it does not add threads to one pair.

### 4.5 Oracle defect candidate: wrong ACK ids after incremental updates (3.5-dev8)

`peers.c:1833-1834` (commit `f12252c7a`, "Fix update message parsing during a full resync"):
`if (p->learnstate != PEER_LR_ST_PROCESSING) st->last_get = htonl(update);` — `update` is read raw
from the wire for a full update (so `htonl` = `ntohl` is right) but computed as `last_get + 1` in
host order for an incremental one, and gets byte-swapped. Captured (vectors §V3, 300-request burst,
46 `inc-update`s): the receiver's acks read `updateid=192, 197, 3338665984, 16777417, 16777423,
3539992577, 16777430, 216, …`; the sender ignores the out-of-window ids, so its `last_acked` stays 0
and its reconnect resume point is wrong; `show peers` on the receiver prints `last_get=1048870688`.
**Consequence for Alcyon:** an Alcyon *receiver* acks the correct id (HAProxy senders then resume
correctly); an Alcyon *sender* ignores ack ids outside `(last_acked, last_pushed]` as HAProxy does and
must not disconnect on them. Not reported upstream by me (the user decides; memory rule).

## 5. Wire protocol reference (what the codec implements; vectors in the companion file)

5.1 **Hello** (client → server, text): `HAProxyS <maj>.<min>\n<remote peer id>\n<local peer id> <pid> <relative pid>\n`
(relative pid is always `1`). **Status** (server → client): `200\n` ok, `300\n` try again (local
peer collision), `501` protocol, `502` version, `503` host (line 2 ≠ my `localpeer`), `504` peer
(line 3's id unknown in the section). Version check: major must be 2, minor ≤ 1; a 2.0 client sets
`PEER_F_DWNGRD` on the server side: no heartbeat is sent and teach uses plain `update`.

5.2 **Framing**: `class(1) type(1)`; if `type & 0x80`: `varint len` + `len` bytes of data. Classes:
0 control (types 0 resync-request, 1 resync-finished, 2 resync-partial, 3 resync-confirm,
4 heartbeat), 1 error (0 protocol → connection closed after sending, 1 size-limit), 10 stick-table
(0x80 update, 0x81 inc-update, 0x82 table-define, 0x83 table-switch, 0x84 ack, 0x85 update-timed,
0x86 inc-update-timed), 255 reserved. Maximum message = `tune.bufsize`; a larger one gets
error/size-limit (`PEER_SESS_ST_ERRSIZE`).

5.3 **table-define** data: `varint sender-table-id`, `varint name-len`, name, `varint key-type`
(2 sint, 4 ipv4, 5 ipv6, 6 string, 7 binary), `varint key-len` (string: `len+1`, measured 33 for
`len 32`), `varint data-types bitfield` (bit = `STKTABLE_DT_*` index, 0..26), `varint expire-ms`,
then for each frqp type set, in bit order: `varint type-index`, `varint period-ms`. The receiver
maps name → its own table (key type must match, else protocol error since `1696cfaa1`), remembers
sender-id → table for `table-switch`/ack, and the bitfield → which values each update carries.
A define is sent before the first update of a table on a session and whenever the sender's
"current table" changes (`table-switch` if already defined).

5.4 **update** data: `u32be update-id` (absent in inc-*: id = previous + 1), `u32be expire-ms`
(timed only), key (5.1 encodings), then one value per set bit in the define, in bit order:
`STD_T_SINT/UINT/ULL` → varint; `FRQP` → 3 varints (age, curr, prev); `DICT` (`server_key`) →
`varint len` then either `varint id` + `varint strlen` + string (first occurrence) or `varint id`
(cached) — Alcyon skips `len` bytes; arrays (`gpt`, `gpc`, `gpc_rate`) → `n` consecutive values,
`n` from the receiver's own table definition. `conn_cur` is `is_local`: carried on the wire,
**not applied** by the receiver. `server_id`/`gpt*` are `as_is` (replaced); counters are replaced
too (no addition); a `recv-only` table ignores local writes (refused in M3).

5.5 **ack** data: `varint sender-table-id`, `u32be last-received-update-id`. Sent when
`last_get != last_acked` on the next send pass (one per batch, not per update); never during a
teach. The sender keeps `last_acked`; on reconnect it re-teaches from the acked point.

5.6 **Session rules** (measured): one session per pair; a hello for a peer that already has a
session: the receiver answers `200` and kills the **old** session, unless the peer is the local
one (`300`); the loser reconnects after `50 + rand % 2000` ms. Heartbeat after 3 s without
sending; a peer silent for 5 s is dead → close, reconnect (`PEER_RECONNECT_TIMEOUT` 5 s; local
peer 500 ms). Resync at start: ask the local peer for up to 5 s, then a random connected remote
peer for 5 s each (`resync-request`; a `resync-partial` answer marks that peer and tries another),
then "fully updated". Teach (on `resync-request`): stage 1 = entries with `seq > last_pushed`,
stage 2 = from the oldest entry up to the teaching origin, both as timed updates, then
`resync-finished` (or `-partial` if the teacher is not `FINISHED`); the learner confirms. Live
updates resume after the confirm; `tune.peers.max-updates-at-once` (200) bounds one pass.

## 6. Design

### 6.1 Crates and owners

- **`alcyon-peers`** (new): `codec.rs` (varint, hello/status, messages: pure functions over `&[u8]`
  / `&mut [u8]`, fuzzable, no I/O), `session.rs` (state machine per peer: `Accept → GetVersion →
  GetHost → GetPeer → SendSuccess | Connect → GetStatus → WaitMsg → Exit/End`, exactly HAProxy's
  `PEER_SESS_ST_*`), `sync.rs` (per-section resync/teach state machine, timers), `show.rs`.
- **`alcyon-stick-table`** grows: `buckets`, `seq`, `apply_remote`, `dirty` API (§6.3), `wire` data
  type table (bit → `StdType`, `is_local`, `as_is`, array len).
- **`alcyon-config`**: `peers` section → `PeersSection { name, local: Option<PeerDef>, remote:
  Vec<PeerDef>, tables: Vec<StickTableConfig>, disabled }`; `stick-table … peers <name>` resolves
  to a section at link time (`"no such peers section"` as HAProxy); `localpeer` / `-L` → `global.localpeer`.
- **`alcyon-rt`**: the peers listener is an ordinary `Proxy` of mode `peers` (as HAProxy's
  `peers_fe`), accepted connections become a `PeerSession` **applet** entry in the session arena;
  outgoing sessions are created by the per-section **sync task**.

### 6.2 Threads

- One **sync task per `peers` section** on one worker (HAProxy rotates sections across threads;
  Alcyon: `section index % nworkers`). It owns the resync state, the timers (reconnect, resync 5 s,
  heartbeat), creates outgoing sessions, and is woken by SIGUSR1/SIGUSR2 for the teach.
- One **session per remote peer**, placed on the worker with the fewest peer sessions (HAProxy's
  `applet_count[]`), all I/O for that peer on that worker. Different peers → different workers;
  with one remote peer the whole sync runs on one worker, like HAProxy — the wire allows nothing else
  (§4.2). The receive side applies updates on the same worker under the bucket lock (§6.5).
- **Request threads** never touch a session: they write their own ring (§6.3).

### 6.3 From `track-sc` to the sender without a shared lock on the request path

Today `update_entry` takes the table's write lock (`table.rs:300`) — a shared lock on the request
path already. **P0 replaces it** with `NBUCKETS = 64` buckets (`RwLock<Bucket>` each, bucket =
`hash(key) & 63`, entries stay in per-bucket `EbMbTree`s + per-bucket expiry/LRU), the same
structure as HAProxy 3.x `buckets[]` (`CONFIG_HAP_TBL_BUCKETS`). The write lock is then per bucket,
held for the counter update only; contention at 32 threads on 64 buckets is measured in P0
(`insreq.sh` on `rules.body` before/after; expected cheaper, must be within +0.5 %).

Dirty marking (P4), on the request thread, inside the bucket write section it already holds:

```
if entry.flags & QUEUED == 0 {            // not already waiting for the sender
    entry.flags |= QUEUED;                // seen by the sender only after it dequeues
    rings[worker].push(slot_idx);         // SPSC: producer = this worker, consumer = the sender
}
```

`rings[worker]` is a fixed-capacity `Pool`-allocated ring of `u32` slot indices per (table, worker)
— `declare_pool!(DIRTY_RING: Pool<DirtyRing>)`, capacity `tune.peers.ring-size` (default 4096,
Alcyon-only tunable; name final in P4). The push is one store to the producer's own slot plus a
release store of the tail: **no lock, no atomic RMW, no global load** (AGENTS.md §8); the consumer
reads the tail with an acquire load. If the ring is full the push is skipped and the entry keeps
`QUEUED` — it stays dirty (`DIRTY_OVERFLOW` flag) and the sender's periodic sweep (every 100 ms,
bucket by bucket) picks it up; nothing is lost, only delayed, and `show peers` counts
`ring_overflows`. This is the same bound HAProxy has: at most one queue position per entry.

The sender (session worker) each pass: drain all `nworkers` rings of each shared table (bounded by
`max-updates-at-once` × 4), and for each slot: `seq = table.next_seq()` (plain increment, sender
only), store `entry.seq = seq`, clear `QUEUED`, set `UNSEEN`, link the entry at the tail of the
table's **update list** (intrusive, `prev/next: u32` in the entry, moving it if already linked).
Then encode from the per-peer cursor `last_pushed` forward: each pushed entry gets `UNSEEN` cleared
(so the next touch re-queues it), `last_pushed = seq`. Ordering is the HAProxy one: by `seq`, one
message per entry, newest state at send time (the entry's counters are read under the bucket read
lock while encoding; HAProxy does the same under `updt_lock` + atomic `ref_cnt`).

Why not HAProxy's `MT_LIST` + tree: the `MT_LIST_TRY_APPEND` is a CAS on a shared list head on the
request path, the tasklet takes `updt_lock` for write under contention with the applet's read —
run 3 shows it costs nothing measurable at 680k/s, so this is not where Alcyon must win; the ring is
chosen because it is what §8 of AGENTS.md permits, and it makes the `insreq` row (§3 iv) trivially
flat: a tracked request does the same work with or without peers except one ring store.

**Remote updates and multiple peers**: an entry written by a remote peer is `apply_remote`'d
(§6.5) and **not** re-queued for other peers (HAProxy does not relay: `updt_is_local == 0` entries
sit in the tree only for teach). On teach, stage 1/2 walk the update list and the buckets.

### 6.4 Sender, acks, reconnect

Per peer: `tx: Buf` (pooled, `tune.bufsize`), per shared table `last_pushed`, `last_acked`,
`last_get`, `teaching_origin`, `remote_id`, `remote_data` bitfield. A pass: acks due → table
switch/define if the current table changed → updates up to `max-updates-at-once` or until `tx` is
full → heartbeat if 3 s idle. Acks received set `last_acked` if within `(last_acked, last_pushed]`,
ignored otherwise (§4.5). On reconnect: `last_pushed = last_acked`, define again, push forward.
Seq wrap (u32) handled as HAProxy: distances, not absolutes.

### 6.5 Receiver

`apply_remote(table, key, Option<expire_ms>, values: impl Iterator<(dt, Value)>)`: bucket write
lock; find or insert the entry (eviction as a local insert; `nopurge` refuses); set expiry = min
(carried, table's); for each carried type that the local table stores and that is not `is_local`:
replace (frqp: `curr_tick = now − age`); `trackers` untouched; entry **not** queued. Unknown or
unstored types are skipped by their encoding (5.4). Key type mismatch, undefined sender table id,
or truncated data → error/protocol, close, as the oracle. `last_get` = the update's id (correct
host-order value; §4.5).

### 6.6 Reload and stop

Master-worker reload (`master.rs:776`): after the new worker has bound (socket handover as today),
the old worker gets SIGUSR1 → its sync task closes remote sessions, connects to **its own `bind`
address** (which the new worker now owns; the old listener is closed first so the connection cannot
land on itself), hello with its own name, teaches everything (`update-timed`), `resync-finished`,
waits for `resync-confirm`, exits. The new worker: the local peer's resync window is 5 s (wall
clock, as HAProxy); then remote. Alcyon keeps HAProxy's "teach only if FINISHED" rule for wire-state
parity **but** treats a node whose remote peers are all unreachable at start as `FINISHED` once
the remote timeout fires (that is HAProxy's documented behaviour too; the measured 0x1 case is the
two-nodes-started-together one and Alcyon will reproduce it — see decision 6 for the alternative).
`hard-stop-after` kills a teach that does not finish. Graceful stop without a successor: close
sessions, no teach. `-x`/`-sf` without `-W`: same as master-worker (the old process is told by
SIGUSR1 as today).

### 6.7 Memory (`memory-2026-10-24.md`)

| object | count | design |
|---|---|---|
| `PeerSession` (state, cursors per shared table, dict skip buffer) | one per remote peer | `Arena` entry in the session arena (applet), `declare_pool!` for its `tables: Vec<SharedTableState>` → fixed `[SharedTableState; MAX_SHARED_TABLES]` or a pooled slice |
| rx/tx buffers | 2 per session | `Buf` from the `buffer` pool, `tune.bufsize` |
| dirty rings | `nworkers` per shared table | `Pool<DirtyRing>` (4096 × u32 = 16 KB each; 16 workers × 1 table = 256 KB; in `show pools`) |
| per-entry | per table entry | `seq: u32, prev: u32, next: u32, shard: u16, flags: u8` = **+16 B** on ≈ 600 B (HAProxy: `eb32_node upd` 40 B + `mt_list` 16 B + `shard`/`seen`/`updt_is_local` 12 B = 68 B) |
| per-table | per table | `next_seq: u32`, update-list head/tail, `rings`, `local_update`, `sync: Option<SectionId>` |
| teach cursor | per session during teach | two `u32` (bucket, slot) — no snapshot, no copy of the table |

Nothing on the request path allocates; `request_allocations.rs` gains a peered-table case (0).
The entry size itself (600 B, ten `Option<SlidingRate>` of 40 B) is a separate finding: HAProxy's
`stksess` for the same `store` list is ~100 B; P0 may pack rates behind the `store` bitmap (not
required for M3, noted for `tradeoff.md`).

### 6.8 Where this differs from `docs/research/multithreaded-peers.md`

That blueprint proposes per-core `SO_REUSEPORT` channels, several TCP connections per pair and a
256-shard table with lock-free channels. Measured: HAProxy **closes** a second session from the
same peer (§4.2), so multi-connection is not wire-compatible and would be Alcyon-only (decision 3);
HAProxy's single session did not lag at the rates this host produces (§4.4), so there is no
measured need; 64 buckets match the oracle's structure and the +0.5 % budget is measured in P0, not
assumed. Its codec section (varint, framing) agrees with the captures.

## 10. Decisions needed from the user

1. **SSL to peers** in M3: refuse by name (proposal; P9 later) or include P9 now (depends on T440's
   rustls client for the `server … ssl` side; the listener side is available today).
2. **`shards`/`shard`**: refuse (proposal; aggregator topologies are not a blog's need) — note that
   `server … shard` is accepted-and-dropped today and will start refusing in P1, which can break a
   config that passes `-c` today.
3. **Alcyon-only multi-session extension (P10)**: not in M3 unless P7 shows a lag (proposal).
4. **`gpt(n)/gpc(n)/gpc_rate(n)` arrays over the wire**: in (proposal; encoding is the scalar one
   repeated, §5.4) — confirm you want them, they cost nothing extra.
5. **Exit criterion wording for Q4**: the task asked for "a rate where HAProxy's sync lags, Alcyon
   keeps up"; on this host HAProxy did not lag at any producible rate (§4.4). Proposal: replace by
   §3's throughput rows (nothing lost, lag ≤ HAProxy's and drained ≤ 1 s, CPU per update ≤
   HAProxy's, request path +0.5 %), measured at night on the same scripts. Alternative: a dedicated
   night run with the receiver pinned to one shared core to force the lag on both (artificial).
6. **Reload teach when the old node is not `FINISHED`** (§4.3): mirror HAProxy (no teach, 5 s local
   timeout, learn from a remote) — proposal, for identical behaviour in a mixed cluster — or
   Alcyon-only improvement: always teach the local successor (the table is still the best copy on
   that host). Either is a one-line condition in P5; the test differs.
7. **P0 scope**: buckets only (proposal) or also pack the 600 B entry (HAProxy ≈ 100 B) in the same
   slice; the second doubles P0's size and risk, and is not needed for M3's rows.
